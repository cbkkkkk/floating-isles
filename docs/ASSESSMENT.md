# 项目评估：缺陷、改造清单与托管迁移

> 这份文档只讲问题，不粉饰。分三块：**一、现在有什么缺陷**，**二、按什么顺序改**，**三、为什么托管/服务器要换、换成什么**。
>
> 标「已确认」的是读代码或实测得到的；标「建议」的是判断，需要你拍板。

---

## 一、缺陷清单

### A. 安全（最要紧，直接决定能不能公开注册）

| # | 缺陷 | 影响 | 状态 |
|---|---|---|---|
| A1 | 前端把后端地址与 publishableKey 硬编码在 `index.html` 里 | 源码一旦公开，端点与密钥形态的字符串随之公开；服务端虽做 Origin 校验，但 Origin 头在非浏览器场景可伪造 | **已确认**。公开版已移除；主线代码仍然存在 |
| A2 | 受信任的 island 使用 `allow-scripts allow-same-origin`，且用户上传的 HTML 走 `blob:` URL（继承父源） | 沙箱可被 iframe 内脚本逃逸，直接读写父页面 DOM / localStorage。现有注释只防「别人的岛」，没防「自己上传但内容不可信」 | **实测确认**：无头 Chromium 控制台打印 `An iframe which has both allow-scripts and allow-same-origin ... can escape its sandboxing.`（2026-11-12，内置岛 iframe） |
| A3 | 同站点 iframe 与主文档共享渲染进程 | 一段 `while(true)` 冻结整个标签页，父页面的超时看门狗一起停摆，前端无自救手段 | **已确认**（架构约束，非 bug） |
| A4 | 参考 schema 把全部函数 `GRANT EXECUTE ... TO anon`，无限流、无配额 | 任何人可反复调用写接口，刷留言、刷计数、耗尽服务额度、塞满数据库 | **已确认** |
| A5 | `fi_island_add` 允许匿名上传任意 HTML 全文并入库 | 存储型 XSS / 钓鱼页 / 外带请求；没有内容审核、没有举报、没有封禁 | **已确认** |
| A6 | 没有 CSP 响应头、没有 SRI、没有错误上报 | 一旦注入成功没有第二道防线，出问题也发现不了 | **已确认** |
| A7 | 身份基于 `localStorage` 里的随机 cid，`fi_claim` 靠旧 cid 认领 | 清缓存即换人，cid 可伪造，不足以做真实账号体系 | **已确认** |

### B. 架构与数据

| # | 缺陷 | 影响 |
|---|---|---|
| B1 | `fi_world` 一次返回**全部**岛屿元数据，无游标分页、无上限 | 作品上千后响应线性膨胀，首屏与每次轮询都拉全量 |
| B2 | `fi_island_html` 返回 HTML 全文，无大小上限、无缓存策略 | 2 MB 作品 × 并发拉取会打满带宽；前端虽有 blob LRU，服务端没有 |
| B3 | 岛的坐标由相机朝向算出，不是世界固定坐标 | 这是「取景框」而非「可漫游的世界」；无论加多少岛，看到的结构都差不多 |
| B4 | `server/schema.sql` 只有 15 个函数，缺少实际部署的 `fi_island_add` | 文档与线上实现漂移，照着这份文件重建会得到残缺后端 |
| B5 | 单文件 6200+ 行 / 287 KB，HTML+CSS+JS 全内联，无模块、无测试、无构建 | 改动靠字符串定位，回归全靠手工，无法多人协作 |
| B6 | 三座内置岛各自内联一份 three.js（940 KB / 918 KB / 855 KB） | 首屏潜在 2.7 MB；同一份库重复下载三次 |
| B7 | `?fill=1` 用示例副本补足 11 座 | 是演示数据，虽然有角标，但容易被误读成真实作品数 |
| B8 | 时辰跟随**本机**时间 | 不同设备看到的世界不同步，「同一个世界」的叙事不成立 |

### C. 产品与运维

| # | 缺陷 | 影响 |
|---|---|---|
| C1 | 没有作品审核状态机、举报、管理员、黑名单 | 开放注册等于开放滥用 |
| C2 | 没有内容备份 / 导出机制，托管额度耗尽后数据进入暂停态且保留期有限 | 有真实用户后存在数据丢失风险 |
| C3 | 错误提示把 403 / 501 / 超时 / 无 SDK 全压成「网络不通」 | 用户和排查者都无法区分故障类型 |
| C4 | 无自动化验证（构图重叠、语法、资源可达都靠临时脚本） | 改一处布局可能在别处产生穿插，缺少回归网 |

## 二、需要改的地方（按优先级）

### P0 — 公开之前必须做完

1. **把用户 HTML 迁到跨站点隔离域**。判据：浏览器任务管理器里主站与岛的进程 ID 不同。同 eTLD+1 的子域不算隔离，必须是另一个可注册域或挂在 PSL 上的平台域。
2. **拆掉 `allow-scripts + allow-same-origin` 的组合**。自己的岛也按不可信处理，时辰/尺寸统一走 `postMessage` 桥，别再读 `contentDocument`。
3. **所有写接口加鉴权 + 频率限制 + 配额**。建议按 cid/uid 做令牌桶，写操作 10 次/分钟、上传 3 次/小时，超限返回明确错误码。
4. **上传链路加服务端扫描**：文件大小 ≤ 2 MB、必须自包含、禁止外链、静态扫描死循环与 `top.location` 等危险模式、人工复核后再发布。
5. **配置 CSP 与安全响应头**，静态托管侧至少 `X-Content-Type-Options`、`Referrer-Policy`、`frame-ancestors`。

验收数字：跨站进程 ID 不同；恶意样本 6/6 被拦；写接口压测 1000 次被限流；控制台 0 个 CSP 违规、**0 条 sandbox escape 告警**（当前为 1 条，可作为修复前后的硬指标）。

### P1 — 让世界真的能长大

6. `fi_world` 改**双列游标分页** `(published_at, id)`，单列游标在同秒发布时会跳项；每页 24 条。
7. 作品表加审核状态机 `draft → pending → approved → published → suspended`，作者不能自审（列级 `REVOKE UPDATE(status,...)`）。
8. 抽出 `lib/` 公共依赖，三座内置岛改为共享一份 three.js，首屏目标压到 < 1 MB。
9. 把布局常量（`ISLE_COUNT`、`BASE_SCATTER`）、构图验收脚本固化成仓库内的自动检查，提交前必须跑通「1200 用例 0 重叠」。
10. 世界时间改由服务端下发，或至少统一 UTC+8 基准，不再各看各的钟。

### P2 — 产品化

11. 举报 / 管理后台 / 黑名单 / 内容导出。
12. 错误码分层，前端按 `auth / quota / timeout / offline / server` 分别给文案。
13. 拆分单文件为模块 + 引入最小构建；补单元测试与端到端冒烟。
14. 决策：要不要把「取景框」改成真正的固定坐标世界。这一步会牵动整个漫游手感，**建议单独评审，不要顺手改**。

## 三、服务器 / 托管为什么要换

### 现状的问题（这些是平台约束，不是配置能调好的）

当前运行形态是「平台托管静态站 + 平台捆绑的云服务」，绑定的应用身份同时决定域名、后端 Origin 与额度。具体限制：

- **额度制**：单应用每月一份固定资源点，数据库 CPU、调用次数、存储、流量、验证码都从里面扣；**用尽后云服务自动暂停**，暂停期间数据不能访问也不能导出，只保留有限天数。
- **域名与 Origin 强绑定**：发布必须复用同一个应用身份，换域名会让登录失效；想挂自己的域名、上 CDN、配 WAF 都受限制。
- **不能单独关闭后端**：想释放名额只能删除应用，而删除会永久删掉数据、文件和注册用户。
- **预览与线上共用一套数据**，测试写入会进正式库。
- **平台锁定**：表、函数、SDK 都围绕该平台设计，迁走时后端要重写。

对一个「给陌生人上传 HTML」的项目，这些约束尤其不合适：上传和注册恰恰是最耗额度、最容易被刷的行为，而额度耗尽的结果是整个服务暂停。

### 目标架构

```
静态前端  →  独立静态托管（可换域名 / 可上 CDN / 可配 CSP）
     ↓ 只走 HTTPS API
自建后端  →  鉴权 + 限流 + 上传扫描 + 审核 + 对象存储 + 数据库
     ↓
用户 HTML →  跨站点隔离域（与主站不同 eTLD+1），iframe 沙箱加载
```

前端与后端解耦之后，`config.js` 里的三个值就是唯一需要改的地方；这个仓库的离线版已经按这个结构留好了口子。

### 三条路线

| 方案 | 做法 | 优点 | 代价 | 适合 |
|---|---|---|---|---|
| **A 纯静态，不要后端** | 只发这个仓库到静态托管，账号/上传/留言全部关闭 | 零运维、零额度、零攻击面、最省钱 | 失去社区功能，只能当作品展示 | **现在就想公开，推荐先这样** |
| **B 自建后端** | Node/Fastify 或 Go + PostgreSQL + 对象存储 + 独立隔离域，自己管域名、证书、备份 | 完全可控，限流/审核/ moderation 都能按需要做 | 需要服务器运维、监控、备份策略，成本最高 | 真要做开放社区 |
| **C 独立 BaaS 项目** | 换一个独立的托管后端项目（自建账号、自己的库），静态前端仍放 Pages | 折中，不用管数据库机器 | 仍有平台额度与 Origin 绑定，只是换了家 | 想快速验证产品 |

**推荐顺序**：先 A 上线（把项目和 README 公开，收集反馈），确认真有人要上传了，再按 B 做后端。不要在还没有真实用户的时候就先背上一台服务器。

### 迁移检查单

1. 先从现有云控制台**导出全部数据**（正常运行期间才能导出，暂停态不行）
2. 选定自有域名，配好 HTTPS 与 CSP 响应头
3. 用户 HTML 单独放到隔离域，确认跨域进程分离
4. `config.js` 只填自己后端的 publicConfig，**真实值不进仓库**
5. 后端实现 `server/schema.sql` 里缺的 `fi_island_add`，并补齐限流与审核
6. 双跑观察 7 天：错误率、上传成功率、单请求耗时、资源用量
7. 确认无误后下线旧应用——注意旧平台删应用会连带删数据，所以第 1 步必须先做完

---

## 四、一句话总结

**画面和交互已经能打动人，但「让陌生人上传任意 HTML」这件事的安全、限流、审核和托管额度都还没准备好。**建议把这个仓库作为公开的前端快照先发出去，后端与服务器等到产品方向确认后再重建，别在演示阶段就承担生产风险。
